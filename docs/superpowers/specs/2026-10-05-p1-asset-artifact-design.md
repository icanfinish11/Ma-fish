# P1 规格：作品与制品（加密存储、上传校验、元数据、签名下载）

**状态**：待评审
**上游**：`2026-10-04-vibe-coding-auction-platform-design.md`（平台级架构，本文只补 P1 的实现级决定）
**预检依据**：`../notes/2026-10-05-p1-preflight-verification.md`（全部数字均为实测）

---

## 1. 目标

把平台级设计里 P1 的那一行落地：**作品 / 版本 / 元数据 / 所有权历史、上传校验、加密存储、元数据解析、签名下载**。

**P1 结束时应当为真的一句话**：一个创作者可以上传一个 `.zip`/`.tar.gz` 项目包；平台在**不解压、不执行、明文不落盘**的前提下判定它是否安全、抽出可浏览的元数据、以 AES-256-GCM 分块加密存储；只有通过访问判定的人才能拿到一个 ≤5 分钟、单次有效的签名下载链接，且每次下载都留下审计；作品的所有权流转以 append-only 历史记录，制品本身**永不复制**。

**P1 明确不做**：上架、出价、拍卖、托管、结算（P2/P3）。P1 结束时作品**存在但不可交易**。

## 2. 决定（每条附预检依据）

### D1 · 接入流程：**加密即入库，再解密校验**

zip 的中央目录在文件**末尾**，单趟前向流无法校验。三个候选里只有一个是「明文不落盘 + 不把 1GB 读进内存」都满足的：

1. 客户端流式上传 → 嗅探 magic bytes → **立即流式加密写入制品库**（明文从不落盘、从不整份进内存）。
2. 用 `yauzl.fromRandomAccessReader` 实现一个**按需解密**的随机访问读取器（zip 先读尾部中央目录）。
3. 校验失败 ⇒ **删除已写入的密文对象**并返回错误。
4. 校验通过 ⇒ 用同一个读取器抽元数据、写库。

**代价（如实记录）**：被拒的上传仍会消耗一次写入 + 一次删除的 I/O。换来的是验收 §13.2「无任何文件落地」**结构性成立**——被拒上传连明文临时文件都不存在，而不是靠清理逻辑兜底。

### D2 · 制品存储格式（**已回填为交付形态**：R1–R6 + I3）

> **本节的旧稿已作废。** 旧稿写的是 `[头][块索引][块数据]`、头里含 `plaintextLength(8) | chunkCount(8)`、
> 索引字段叫 `nonceSuffix(8)`。**那个排布单趟前向写不出来**（两个总量字段要等流结束才知道，
> 而索引排在数据之前），实施期由控制器裁定 R1–R3 改成本节这个形态并复审通过；
> nonce 拆分由最终全分支审查的 I3 再改一次（见 D4）。
> 裁决原文与证据：`../plans/2026-10-05-p1-asset-artifact.md:163-177`（R1–R6）。
> **本节与 D3/D4 是现行真值**；计划里那段是历史裁决记录，冲突时以本节为准。

```
[ 文件头 35+N ]   magic(4)="VCA1" | formatVersion(2)=2 | keyIdLen(1) | keyId(N) |
                  fileId(16) | chunkSize(4) | noncePrefix(8)
[ 块数据 ... ]    逐块 ciphertext || tag(16)，顺序追加
[ 块索引 ... ]    每块定长 24 字节：
                  offset(8, **文件绝对偏移**) | ciphertextLength(4, **不含 tag**) |
                  记录自称序号(8, 大端, **仅供比对**) | 保留(4, 全零)
[ 尾部 24 字节 ]  indexOffset(8) | chunkCount(8) | plaintextLength(8)  ← **恒为文件最后 24 字节**
```

头里**只放流结束之前就已知的字段**（`fileId` / `chunkSize` / `noncePrefix` 在构造期就有），
两个总量字段搬进**恒为最后 24 字节**的尾部。于是写入端是**真正的一趟顺序追加**
（头 → 逐块密文 → 索引 → 尾），读取端从末尾 24 字节一路往前定位（读尾 → 读索引 → 按需取块）。

块索引必须**定长且可定位**，以便随机访问只解密需要的块。

**定长头的算术**（R1：旧稿的「48」是笔误，旧字段之和是 47）：
`4 + 2 + 1 + 16 + 4 + 8 = 35`（I3 把 `noncePrefix` 从 4 字节加宽到 8 字节，见 D4）。
要让定长头再变宽，那是一次 `formatVersion` 递增，**不是**把某个字段悄悄加宽。

### D3 · **块序号契约（预检发现的缺陷，必须写进实现约束）**

**读取器必须用「读取位置」推导 nonce 与 AAD，并显式校验「索引记录自称的序号 === 读取位置」；
绝不能信任记录里自称的序号。**

预检实测：若信任自称序号，攻击者把两条存储记录**整体调换**，AAD 输入随之调换 ⇒ **认证通过、明文被静默重排**。加上位置校验后，调换会在位置 0 处被点名拒绝。

**这一条正是索引里那个 8 字节字段存在的唯一理由**：它是「位置 P 处的记录自称序号 Q」这条校验与
其错误信息的**数据来源**，**绝不参与** nonce / AAD 推导。
旧稿把它叫 `nonceSuffix`——**那个名字本身就会诱发这个缺陷**（它暗示这个字段是 nonce 的一部分、
于是可以被信任）。现行名称是 **`记录自称序号`（`IndexEntry.index`，仅供比对）**。

**这条必须有专门用例**（「调换两条记录必须被拒」），否则它会悄悄退回去。

### D4 · nonce 方案

`noncePrefix(8 字节，每文件随机) || 块序号(4 字节大端)`，共 12 字节。

- 同文件内块序号唯一 ⇒ nonce 唯一；
- 跨文件靠 8 字节随机前缀区分：前缀空间 2^64 ⇒ **生日界不再是现实约束**；
- 4 字节计数器是 D6 合法制品块数上限的**两个数量级以上**（1 GiB / 8 MiB = 128 块，
  上限 2^32）；读取端对 `position ≥ 2^32` 必须**响亮拒绝**，绝不静默截断；
- **禁止**「固定前缀 + 从 0 开始计数器」跨文件复用——GCM 下 nonce 重用不只泄露明文异或，
  **还会暴露认证子密钥（即在该密钥下的可伪造性）**。

**I3 裁定（最终全分支审查，2026-10-05；这是规格级决定）**：上一版是
`noncePrefix(4) || BE64(块序号)`。文件内唯一成立，但**跨文件在同一把密钥下生日界生效**：
约 9.3k 份制品 ⇒ 至少一次前缀碰撞的概率约 1%；约 65k ⇒ 约 39%。而 P1 里没有任何东西
强制或触发密钥轮换。改成 `8 随机 || BE32(计数器)` 之后 2^32 的计数器仍远超块数上限，
而 2^64 的前缀空间把生日界推到不可达的量级。**代价与决定**：

- **`formatVersion` 从 1 递增到 2**。理由：nonce 的拆分方式是**格式契约的一部分**（它不写在制品字节里，
  只能由版本推出来）。不递增版本的话，一份 v1 制品会被新读取器按新拆分解密 ⇒ 认证失败，
  而报出来的是「密文被篡改」——一个**指错了原因**的错。递增版本让旧制品得到
  「不支持的 formatVersion」这句正确的拒绝。**P1 没有生产数据，这是最便宜的时刻**。
- 定长头随之从 31 变成 **35**（`noncePrefix` 4 → 8），`noncePrefix` 是唯一变宽的字段。

AAD 绑定 `fileId | position | 是否末块`（**本次改动没有碰 AAD 的任何一部分**）。末块标记是
**截断检测**的依据（预检已验：截断末块会被拒）。

### D5 · 密钥与轮换

- 主密钥由环境注入（`ARTIFACT_KEYS`：JSON `{keyId: base64(32字节)}`，配合 `ARTIFACT_ACTIVE_KEY_ID` 指定当前写入键），**不入库、不入 git**；沿用 P0 的占位值拒绝机制。
- 文件头带 `keyId`。解密按 `keyId` 选密钥 ⇒ **轮换 = 新增一个 keyId 并让新写入用它**，旧制品继续按其 keyId 可读。
- 密钥环形如 `{ [keyId]: Buffer }`，当前写入键由 `ARTIFACT_ACTIVE_KEY_ID` 指定。
- 缺失当前写入键、或遇到未知 keyId ⇒ **拒绝**（不是回退到默认键）。

### D6 · 归档校验限制（取自设计文档威胁 #2，全部实测可执行）

| 限制 | 值 |
|---|---|
| 累计未压缩大小 | ≤ 1 GiB |
| 条目数 | ≤ 20,000 |
| 压缩比 | ≤ 100:1 |
| 路径 | 拒绝绝对路径、`..` 段、反斜杠分隔符穿越 |
| 链接 | 拒绝 symlink 与 hardlink |
| 类型 | 仅 zip 与 tar.gz，以 magic bytes 确认 |

**两条实现约束来自预检**：

1. **解析器抛错必须计为「拒绝」，不能让进程崩掉**——yauzl 自带 zip-slip 防护会在 open 阶段抛错；一次恶意上传不该变成一次未处理异常。
2. **不能只依赖解析器自带的防护**——它不覆盖 symlink，也不覆盖聚合限制。

### D7 · 归档类型嗅探

用 `file-type`，判定条件为 `ext === 'tar.gz' || mime === 'application/gzip'`。

**预检实测**：`file-type` 对 gzip 压缩的 tar 返回 `ext: 'tar.gz'`，**不是 `'gz'`**。写成 `=== 'gz'` 会把 **100% 的合法 tar.gz 上传全部误拒**。

### D8 · tar.gz 流式校验

- 用 tar 包的 **`'entry'` 事件**（不是 tar-stream 的 `onentry` 回调；用错会**静默挂住**，不报错）。
- 累计大小与压缩比**仅凭 tar 头部**判定（头部声明的 size 就是分帧依据），因此炸弹在解压出几百字节时即被中止。
- 提前中止 = **销毁上游 + 立刻 settle 自己的 promise**；仅停止消费会死锁，无脑 drain 等于把炸弹解完。`tar.Parser` 没有 `destroy()`。

### D9 · 元数据：**纯静态解析，绝不执行**（C2）

从归档中读取（全部为读取，绝不写入、绝不执行）：

- `README*`：取第一个匹配，截断到上限；
- 文件树摘要：路径 + 大小，深度与条目数受限；
- 语言分布：按扩展名归类，按字节数占比；
- 依赖：解析 `package.json` / `requirements.txt` / `go.mod` 等**文本**清单；
- 完整度评分：按设计文档 §6.2 的默认权重，权重可配置。

**禁止**：不运行 `npm install`、不执行任何脚本、不跟随链接、不解析需执行的格式（如 `.pyc`、二进制）。

### D10 · 签名下载

- HMAC-SHA256 签名，载荷含 `assetVersionId | userId | expiresAt | nonce`。
- TTL ≤ 5 分钟（设计文档威胁 #3）。
- **单次使用**：`nonce` 存 Redis，首次使用即消费；重复使用 ⇒ 拒绝。
- 签名校验用**定时安全比较**。
- 每次下载写 `AuditLog`（成功与失败都写）。

### D11 · 访问判定与所有权历史

- 制品模块对外接口沿用设计文档 §3.2：`store / readMetadata / checkAccess / signDownloadUrl`。`checkAccess` 是**唯一的**授权入口（P0 的默认拒绝策略在此延续）。
- `OwnershipHistory` 为 **append-only**：纳入 P0 已建成的双角色 `REVOKE` 机制（属主角色跑 DDL、`app_user` 无 `UPDATE`/`DELETE`）。
- 所有权转让 = `Asset.owner` 指针变更 + `OwnershipHistory` 追加一行，**不解密、不复制制品**（设计文档 §5.2 第 2 条）。

### D12 · 数据结构

沿用设计文档 §5.1 与 §5.3：`Asset` / `AssetVersion` / `AssetMetadata` / `OwnershipHistory`。
新增 Postgres schema `asset`（每模块自有 schema，C5）。所有时间戳 `@db.Timestamptz(3)`（C6，P0 已确立）。主键 UUIDv7（复用 `@vca/shared` 的 `uuidv7`）。

## 3. 验收判据

| # | 判据 | 验证方式 |
|---|---|---|
| 1 | 八个归档样本判定正确：**六个恶意全拒、两个合法全接受** | 集成测试，含合法样本（否则「全拒」也能骗过测试） |
| 2 | 恶意样本**零文件落地** | 校验前后比对制品库与临时目录，断言无新增 |
| 3 | 调换两条密文记录必须被拒 | 单测（D3 的专门用例） |
| 4 | 篡改任一块密文必须被拒并点名块号 | 单测 |
| 5 | 截断末块必须被拒 | 单测 |
| 6 | 加解密往返一致（含跨块、末块不满、空文件） | 单测 |
| 7 | 未知 `keyId` / 缺失主密钥 ⇒ 拒绝，且**不回退**到默认键 | 单测 + 引导期校验 |
| 8 | 签名 URL 超时、篡改、重复使用**三种情况各自**被拒 | 集成测试（真 Redis） |
| 9 | 每次下载（含失败）都写审计 | 集成测试查真库 |
| 10 | `OwnershipHistory` 在运行时角色下 `UPDATE`/`DELETE` 被真实拒绝 | 集成测试（沿用 P0 的 append-only 断言方式） |
| 11 | 未授权用户无法取得签名 URL | 越权矩阵（沿用 P0 的安全测试骨架） |
| 12 | 元数据解析**绝不执行**归档内容 | 用一个含可执行脚本的样本，断言其未被运行（副作用探针） |
| 13 | 内存上界与文件大小无关 | 端到端取**已落盘字节的推进**：载荷 > `2 × CHUNK_SIZE` 时，**客户端仍在发送期间**盘上必须已出现 ≥ 载荷 − `2 × CHUNK_SIZE` 的制品字节（「攒够再写」的实现恒为 0）。**不用 RSS**；「未完成字节数」只作为诊断量报出——它含内核 socket 缓冲与 multipart 分帧，**与主机相关**，不作为判据 |
| 14 | **制品身份必须与版本记录比对**（I1）：下载路径读出的 `fileId` ≠ `asset_versions.file_id` ⇒ 拒绝（500 `ASSET_ARTIFACT_UNREADABLE`）且**零字节** | 集成测试：把对象换成**等长**的另一份合法制品（明文字节数相同、末块标记正确、归档校验全过）必须被拒——只核长度**不是**身份 |

## 4. 不在范围内

- 上架 / 出价 / 拍卖 / 托管 / 结算（P2、P3）
- 病毒扫描、沙箱预览、自动截图（P5+；C2 明确禁止执行用户代码）
- 对象存储后端（P1 用本地加密卷；接口留出 seam，但不建 S3 适配器——无第二个调用方）
- 前端任何形态

## 5. 已知未验证面（实现时**先验再做**）

1. **上传路径**：NestJS 12 / Express 5 下 multipart 流式接入与硬性大小上限（`multer` 2.4.0 存储引擎选择）。**这是 P1 最大的未验证面**，必须在第一个任务里用探针确认，而不是照计划假设。
2. **随机访问读取器**与既有的分块加密格式的映射（含「只解密尾部若干块」的效率）。
3. **校验失败后删除密文对象失败**时的处置（重试？留待清理？必须有明确决定）。
4. 8MB 真实块大小下的 AAD/nonce 逻辑（预检用 64KB 块）。
