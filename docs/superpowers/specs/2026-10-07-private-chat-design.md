## 0 这份文档回答什么

交换的双方需要能说话。而平台今天**没有任何私聊能力**——实测：`docs/superpowers/{specs,notes,plans}` 全部六个文档里，`私聊|聊天|站内信|沟通|消息` **各只有 1 处命中，且都是「会话」「消息队列」这类无关词义**。设计文档 §2.1 的阶段表里也没有它。

同时用户决定：**先不开发竞拍功能**（是否后续继续，暂定）。

⇒ 本文件把私聊交流定为 **P4**，并把它需要的东西定清楚。

| # | 决定 | 来源 |
|---|---|---|

## 2 模块与边界

新模块 **`chat`**，自己的 Postgres schema（C5：一模块一 schema）。

**依赖方向**：`chat` **不** import `exchange` / `dispute`。反向才是允许的：`exchange`/`dispute` 通过**一条单向接口**向 `chat` 写系统事件。

> **依据**：P3 预检 §0.2 实测过——按「只加在这里」的直觉在 `asset` 与 `exchange` 之间造成环，仓库自己的 `no-circular` **报 6 条 error / exit 6**（单向则 0 违规）。而绕过接缝也实测存在（`PolicyGuard.registerCondition`：条件由各模块注册，守卫不 import 业务模块）。
> **⇒ 本设计的纪律**：**系统事件的写入是一条从业务模块指向 `chat` 的单向边**，而 `chat` 对业务一无所知。

## 3 数据模型

### 3.1 `chat.threads`

| 列 | 说明 |
|---|---|
| `id` | UUIDv7（C4）|
| `user_a` / `user_b` | 双方 |
| `context_kind` | `GENERAL` / `OFFER` / `CONTRACT`（**闭集**，配运行期执行者）|
| `context_id` | 上文的 id；`GENERAL` 时为空 |
| `created_at` / `last_message_at` | `@db.Timestamptz(3)`（C6）|

**★ 三条约束，每条都有理由**：

1. **`CHECK (user_a < user_b)`（规范化排序）** —— 让「同一对人」**只有一种表示**。
   *理由*：没有它，`(a,b)` 与 `(b,a)` 是两行合法的数据，而「一对一线程」会在并发下退化成两条。**唯一约束只有在表示唯一时才有意义。**
2. **`UNIQUE NULLS NOT DISTINCT (user_a, user_b, context_kind, context_id)`** —— PG16 支持。
   *理由*：`GENERAL` 的 `context_id` 为 NULL，而 SQL 的默认语义是「两个 NULL 不相等」⇒ 普通唯一索引会**允许无数条 `GENERAL` 线程**。用 nil-uuid 冒充 NULL 也能绕，但那是拿一个假值去补一个真语义。
3. **条件化 CHECK**：`(context_kind = 'GENERAL') = (context_id IS NULL)`（照 P2 的条件化 CHECK 写法）。

### 3.2 `chat.messages` —— **只能追加**

| 列 | 说明 |
|---|---|
| `id` / `thread_id` / `created_at` | |
| `kind` | `HUMAN` / `SYSTEM`（**闭集**）|
| `sender_user_id` | `HUMAN` 时必填，`SYSTEM` 时为空 |
| `body` | 文本，长度有界 |
| `system_event` | `SYSTEM` 时的**事件种类（闭集）**，配**运行期执行者** |

**条件化 CHECK**：`kind = 'HUMAN'` ⇔ `sender_user_id IS NOT NULL AND system_event IS NULL`。

**逐表 `REVOKE` UPDATE/DELETE**（C7），配真库断言与 `aclexplode` 见证（P2 的标准）。

> **★ 运行期执行者不是可选项。** P3 预检 §E 实测：`kind='NOT_A_KIND'` **过账成功并落库**——**CHECK 无法枚举一个闭集，运行期守卫是应用层的责任**。⇒ `kind` 与 `system_event` **各需一个 `assertXxxKind`**，并各配一条「未知值被拒」的两方向见证。

### 3.3 ★ 两个「每人一份」的状态放在**独立表**，不放在消息行上

| 表 | 语义 |
|---|---|
| `chat.message_hides` | `(message_id, user_id, hidden_at)` —— **我从我的列表里隐藏** |
| `chat.thread_reads` | `(thread_id, user_id, last_read_at)` —— **我读到哪儿了** |

> **★★ 这是本设计里最要紧的一条，理由值得写下来**：
> 这两件事是**每个用户各自的事实**，不是消息的属性。若把它们做成 `chat.messages` 上的列（`hidden_by_a` / `hidden_by_b`、或 `read_at_a` / `read_at_b`），那么「隐藏一条消息」「标记已读」就**必须 `UPDATE` 那一行**——**而那正好与 §3.2 刚立下的「只能追加 + REVOKE UPDATE」直接冲突**。
> **⇒ 把「每人的事实」放在共享行上，会逼着实现者把自己刚立下的纪律破掉**（要么改纪律，要么让这两个功能变成 `UPDATE` 的例外，而「例外」正是本项目反复抓的那一类）。
> **⇒ 正确的形状是：共享的不可变，各自的放各自的表。**

## 4 接口（全部轮询友好）

| 路由 | 作用 |
|---|---|
| `GET /chat/threads` | 我的线程列表（含未读数）|
| `POST /chat/threads` | 解析或创建（对方 + 上下文）——**幂等**：同一对同一上下文永远解析到同一条 |
| **`GET /chat/threads/:id/messages?after=<cursor>`** | **轮询端点**。游标式 ⇒ 将来换 SSE 只换传输，不动表 |
| `POST /chat/threads/:id/messages` | 发送。**确定性幂等键**（由 `(threadId, senderId, clientKey)` 派生）|
| `POST /chat/messages/:id/hide` | 个人隐藏（写 `message_hides`，**不触消息行**）|
| `POST /chat/threads/:id/read` | 推进已读位点（写 `thread_reads`）|

**限流**：档位是**闭集**（5 档，威胁 #13 的投影）。⇒ 挑语义最近的一档，并**记录档名不吻合**，不凭空发明安全参数。

> **依据**：同一条纪律在 P1（下载挂 `search`）与 P3（交换挂 `bid`）上各用过一次，两次都是「记录不吻合」而不是「发明一个数」。

## 5 系统事件（跨模块，全部单向）

`exchange`（将来的 `dispute`）在状态变化时，通过一条单向接口把**只读系统消息**写进对应线程：

```
ChatPort.recordSystemEvent(tx, {
  context: { kind: 'OFFER' | 'CONTRACT', id },
  event: SystemEventKind,          // 闭集
  payload: …                       // 规范化，供渲染
})
```

**要点**：
1. **必须在调用方的事务里**（收 `tx`，且**必填**）。
   > **依据**：P2 的 C-1 裁定（可选参数让错误调用合法）与 P3 Task 1 的实测更正——**「必填」不是机器守卫**（`PrismaService` 满足 `Prisma.TransactionClient`，实测编译通过）。⇒ 参数类型用 **`Prisma.TransactionClient & { readonly $connect?: never }`** 这条否定约束。
2. **事件种类是闭集 + 运行期执行者**（同 §3.2）。
3. **系统消息不可由人伪造**：`kind='SYSTEM'` 的写入路径只有这一条接口，HTTP 发送端点必须拒收 `kind`。

## 6 授权

- **只有线程的两个参与者**能读该线程、能在其中发消息。
- 拒绝面：非参与者读 ⇒ 403/404（**不泄露线程是否存在**）；往自己不在的线程发 ⇒ 拒。
- **每一条拒绝都要有接受对侧**（本项目标准：一个什么都拒绝的检查证明不了任何东西）。
- 六个新路由都要进**两条覆盖率门的逐路由断言**与**越权矩阵**（ledger × 四角色 → chat × 四角色）。

## 7 明确不做（C16）

| 不做 | 理由 |
|---|---|
| **WebSocket** | 设计文档 §:80 已表态；且要新增依赖，与「不加依赖」的一贯纪律相抵。表结构已为 SSE 留口 |
| **SSE（本轮）** | C3 选了轮询优先；换传输不动表 |
| **陌生消息治理**（举报 / 拉黑）| C2：暂不做；**需要时先加这两件** |
| **附件 / 图片** | P1 的制品路径将来可承载；现在做等于预埋一条没有消费者的存储路径 |
| **正在输入 / 在线状态** | **这两件恰是轮询最不擅长的**——明确排除，而不是含糊带过 |
| **消息搜索** | 无需求证据；且它对 append-only 表要额外索引 |
| **消息编辑** | 与 C4 直接冲突 |

## 8 验收判据（可独立复核）

| # | 判据 |
|---|---|
| 1 | **规范化的对**：`(a,b)` 与 `(b,a)` 落进**同一条**线程（真库双方向）|
| 2 | **`GENERAL` 线程唯一**：并发创建同一对 ⇒ 恰好一条（`NULLS NOT DISTINCT` 承重）|
| 3 | **只能追加**：`UPDATE`/`DELETE` 被拒**且行未变**（不是「抛错就算」）|
| 4 | **闭集执行者**：未知 `kind` / 未知 `system_event` 被拒（各一方向 + 接受对照）|
| 5 | **授权**：非参与者读/写被拒；参与者读写通过（越权矩阵 × 四角色）|
| 6 | **游标轮询**：连续轮询**不重不漏**（含并发写入者插入的情形）|
| 7 | **系统事件单向**：`exchange` 写系统消息后 `pnpm arch` **0 违规**（预检 §0.2 的反面见证）|
| 8 | **系统消息不可伪造**：HTTP 发送端点拒收 `kind='SYSTEM'` |
| 9 | **个人隐藏不影响对方**：A 隐藏后 B 仍可见、且消息行未变 |
| 10 | **幂等**：同键重发不产生第二条消息 |

## 10 未决与风险（据实，不隐瞒）

| # | 未决 / 风险 |
|---|---|
| R1 | **限流档位名不吻合**（§4）——按纪律记录，不发明数字。 |
| R2 | **`last_message_at` 是一个共享行上的可变列**，而 §3.3 刚论证过「共享的不可变」。它是**有意的例外**：它是线程的**派生元数据**（可由消息重算），不是「谁的事实」。**若它成为争议点，正确修法是拿掉它、改为查询时聚合**（代价：列表页要多一次聚合）。 |
| R3 | **无删除 ⇒ 存储单调增长**。本轮不设保留策略（无需求证据），但**记下**：一旦有合规或成本要求，这里需要一个策略，且**它不能是硬删**（C4）。 |
| R4 | **`GENERAL` 线程的创建不设门**（C1 任何用户之间）⇒ 一个用户可以给任意多人开线程。**C2 已决定暂不做治理**；风险记在这里，第一批治理件是**举报 + 拉黑**。 |
| R5 | **系统事件的 `payload` 形状**未定死——各事件种类不同。**要求在实现前把每一类的形状写进任务书**，而不是留一个自由 JSON。 |
| R6 | **SSE 的将来形状未验证**（C3 只承诺「不动表」）。**若将来要上 SSE，它需要自己的预检**（长连接 vs 限流中间件 / 优雅关停 / 部署形态——这三件正是 P3 刚实测出问题的地方：`$disconnect()` 取消在飞事务并产生未处理拒绝）。 |

## 11 下一步

按本项目既定流程：**本 spec → 用户复审 → 预检（可运行探针）→ 实现计划 → Subagent-Driven 实现 → 控制器跑完成判据。**

**预检要探的（初稿）**：
- `UNIQUE NULLS NOT DISTINCT` 在本仓的 PG16 上真的可用（写一条实跑）。
- 规范化 `(user_a < user_b)` 在**并发创建**下确实收敛到一条（不是靠应用层查一次再插）。
- 逐表 `REVOKE` 与 `message_hides` / `thread_reads` 的可写性**不冲突**（前者拒绝 UPDATE 到 `messages`，后者要能写自己的表）。
- 游标轮询在**并发插入**下不重不漏（`created_at` 相同的情形）。
- `exchange → chat` 的单向边在 `pnpm arch` 下 0 违规（照 P3 预检 §0.2 的镜像法）。
