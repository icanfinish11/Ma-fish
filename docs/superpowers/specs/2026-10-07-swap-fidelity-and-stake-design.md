## 0 这份文档回答什么

用户提出的三个问题：

1. 双方的代码在交换之前该如何进行检查？
2. 如何保证代码的保真性？
3. 如果有不轨的人先用垃圾内容交换别人的优质内容，然后再申请售后，如何保证用户的权益？

---

## 1 结论：根因不是「质量校验不严」，而是「平台没有任何一处记录双方判的是哪一份」

设计 §1.4 已经把风险划到位了：

> 物物交换是对称的……因此不存在「单方被白嫖」，只存在「换到了垃圾」。真正的风险是信息不对称。

并把平台的责任落在公平、信息对称、售后三件事上。**但这三件事都建立在一个今天不存在的前提上**：能够证明「你当时同意的，与后来交付的，是同一份东西」。

今天的攻击链因此是：

```
保真不可证  →  争议只能争「质量」  →  「质量」没有 ground truth（D7 明确不判）
           →  恶意方可以反咬  →  诚实方无法自证  →  维权失败
```

- **保真不可证**：`SwapContract` 只钉 `assetAId` / `assetBId`（作品级），**没有版本、没有摘要、没有 dossier 快照**（§2 取证 2）。
- **质量不可判**：设计的立场（D7：「商品价值由用户决定」）是正确的，但这个立场**只有在保真可证时才成立** —— 否则「价值不等」与「交付不符诺」混在一起，平台被迫去当价值裁判，而它没有裁判所需的证据。
- **反咬之所以难防**：争议双方都能提（D18），而库里没有任何客观依据可以区分「诚实交付」与「交付了别的东西」。

**修法的分界线**：把争议的判据从「谁的质量更好」（人判、无据）换成「承诺是否被履行」（机器判）。

## 2 现状取证（逐条实核，附文件与行号）

### 2.1 交换前的检查是一道形式门

| 事实 | 证据 |
|---|---|
| 完整度评分的七项里，LICENSE(10) / 截图(15) / 入口脚本(15) **只看条目名，一个字节内容都不读** | `apps/api/src/modules/asset/metadata/parse-metadata.ts:424-448` |
| 资格判据只有「完整度 > 0 且 README 摘录非空」 | `apps/api/src/modules/exchange/core/eligibility.ts:53-74`；P3 计划 D16 |
| dossier 十项里唯一需要新建的是「可看的截图/录屏」，而截图是唯一**平台无法核对**的一项（作者上传，内容不可判） | P3 计划 Task 9 的实测表（行 3761–3771） |

⇒ 一个 10 文件、250 字 README、LICENSE、可解析的 `package.json`、`index.js`、任意 `shot.png` 的**壳工程可以拿到满分 100 并进入交换流程**。

### 2.2 保真没有承诺载体

| 事实 | 证据 |
|---|---|
| `SwapContract` 只有 `assetAId` / `assetBId`，**没有版本、没有摘要** | P3 计划行 885–886；全计划 `asset_version_id` / `sha256` 在 exchange 侧零匹配 |
| 而预览是**按版本**出的（`PreviewManifest.assetVersionId`） | P3 计划行 3840 |
| 版本级摘要**已经存在但没被用**：`AssetVersion.sha256`（明文 sha256，上传时算出） | `apps/api/prisma/schema.prisma:171` |
| 上传新版本的路径不在 P3 的改动半径内，且 `locked_at` 在整个 `apps/` 下**零读取者** | `grep lockedAt\|locked_at` over `apps/` ⇒ 0 匹配；P3 计划文件结构未列 `asset-version.service.ts` |
| 释放事务只转让作品、不做任何内容核对 | P3 计划行 3599–3680 的 `releaseContract` |

⇒ 「交付的就是判过的那一份」既没有**承诺**，也没有**证据**。用户担心的「维权难」，一半难在这里无据可查。
**（据实记好消息）**：版本今天**不可删**（`delete` 只存在于制品存储的清理路径），所以「预览的版本被删掉」这一类攻击今天不成立；这条取证的意义是**证据**（争议可重建），不是拦截。

### 2.3 售后对「纯等值互换」是空的

| 事实 | 证据 |
|---|---|
| 交换不收保证金（保证金是 §7.1 拍卖那一行的事） | P3 计划 D9；「不在 P3 范围内」第 4 条 |
| `RELEASED` 不动钱，钱在 `SETTLED` 才动；`RESOLVED_REVERSED` 被显式判为**不存在** | P3 计划 C31 / D6；`tests/unit/exchange/state-machine.test.ts` 有一条「不存在 `RESOLVED_REVERSED`」的断言（计划行 1567–1571） |
| 补差为 0 时释放事务**连义务行都不建** ⇒ 争议期能冻的只有空气 | P3 计划行 3643 的 `if (contract.topUpAmount > 0n && …)` |
| §10 的「争议败诉 −15 分」在 P3 计划里**零落点**；`creditScore` 列存在但**零写入者** | `grep 信誉\|credit` over P3 计划 ⇒ 0 匹配；`apps/api/prisma/schema.prisma:39` |
| 一个偶然的缓解（据实记载，不是设计）：`locked_at` 永不清空 + `proposeOffer` 拒被锁定的作品 ⇒ 欺诈方刚换到的东西**恰好**不能再拿去发要约 | P3 计划行 2973；但 `unlockAssets` **零调用方**（见 2.4） |

### 2.4 顺带发现的两个既有缺陷（本设计必须一起修）

1. **`unlockAssets` 零调用方** ⇒ 锁的生命周期今天**没有定义**：`CANCELLED` 之后作品永久卡死（合法所有人再也发不出要约），`SETTLED` 之后也无法再交易。⇒ 见 §10。
2. **`locked_at` 的处分冻结只在 `proposeOffer` 一处被检查**（而且是通过 `AssetLockedError` 间接表达的）；P4 的拍卖路径与未来的任何转让路径都还没有这道检查。⇒ 见 §10 的复访触发条件。

### 2.5 押金与罚则的技术底座**已经齐了**（零新增账本语义）

| 需要的能力 | 今天已有的原语 |
|---|---|
| 押金冻结 / 退还 | `LedgerService.freeze` / `unfreeze`（`apps/api/src/modules/ledger/ledger.service.ts:302-319`，§8.2 行 2） |
| 罚没 | `TRANSACTION_KINDS.FORFEIT` **已在 kind 闭集里**（`apps/api/src/modules/ledger/core/types.ts:50`，§8.2 行 3） |
| 跨用户转移 | 通用 `post` / `postLegs`（行 140/180），借贷平衡由 C28 强制 |
| 幂等 | 确定性幂等键 + `(producer, key)` 唯一索引（控制器裁定 ⑤） |

⇒ **增量 B 不需要新增交易 kind、不需要新增账户类型、不需要新的账本原语。**

## 3 分界线：可核对的承诺 vs 不可判的价值

| 问题 | 谁来判 | 本设计的处置 |
|---|---|---|
| Q1 交付的是不是你看到的那一份？ | **机器**（100% 可判） | §5 保真链 |
| Q2 你看到的那一份资料是否忠实于制品？ | **机器**（九项平台自产 ⇒ 天生忠实；作者的话需要核对 ⇒ §6 闭集） | §6 承诺闭集 |
| Q3 这一份东西本身值不值？ | **不判**（D7） | 交给补差、评价、信誉、市场 |
| Q4 判错了之后能不能挽回？ | **机制**（押注 + 回转 + 罚则） | §7 / §8 |

**这条分界线是本设计的承重墙**：凡不在闭集内的申诉事由（「我觉得质量差」「跑不起来」），机器**不判**，移交人工（属 P6）。

## 5 增量 A · 保真链（钉住）

### 5.1 钉什么、钉在哪一刻

`SwapContract` 是在**要约被接受的那一刻**生成的（§6.3 的 `SENT → ACCEPTED → 生成 SwapContract`；落点是 Task 6 的 `accept` 路径，**不是** Task 7 的 `confirmLock`）。在那一刻为双方各写入：

| 字段 | 含义 | 来源 |
|---|---|---|
| `pinnedVersionIdA` / `pinnedVersionIdB` | 当时 dossier 所依据的 `AssetVersion.id` | 预览请求解析出的那个版本 |
| `pinnedSha256A` / `pinnedSha256B` | 该版本的明文摘要 | `AssetVersion.sha256`（已存在） |
| `dossierDigestA` / `dossierDigestB` | 平台生成的 dossier 的**规范序列化**的 sha256 | 新增：`canonicalizeDossier()` 纯函数 |

**规范序列化必须是一个纯函数并单独成文件**（照 `core/` 的先例）：字段顺序、空值、数字格式、数组顺序全部固定，否则「同一份 dossier 两次摘要不同」会让整条链失效。它必须有一条性质测试（同输入 ⇒ 同摘要；字段顺序变化 ⇒ 同摘要；内容变化 ⇒ 摘要变化）。

**接受请求必须带回它看过的那个承诺（TOCTOU 的执行点）**：预览响应返回 `(assetVersionId, dossierDigest)`，而 `POST /exchange/offers/:id/accept` **必须把它们原样带回**。若与当前值不一致（作者在对方看完预览之后、点接受之前上传了新版本），**接受失败**并提示「资料已变更，请重新查看」—— 而不是把接受绑到一份对方从未看过的 dossier 上。这是「钉住」在竞态下的**唯一**正确形状：没有它，`pinnedVersionId` 记的是「平台此刻的版本」，而不是「接受方当时判的那一份」。

### 5.2 校验点（两处，都必须有见证）

1. **`RELEASED` 时**：钉住的版本仍存在、可读，`sha256` 与钉住值一致，dossier 重放摘要一致。不一致 ⇒ 拒绝释放（不是静默放行）。
2. **下载时**：签名下载路径带出 `pinnedSha256`，由**客户端可自校验**（`sha256` 已经在对外契约里，见 `asset.controller.ts:54` 的注释）。

**据实划界**：今天版本不可删、制品不可改，所以校验点 1 在正常路径上**总是通过**。它的价值是证据与将来（一旦有人加了删除/替换能力，这里就是执行点）。**不要**把它宣传成拦截。

### 5.3 dossier 的规范内容（进入摘要的九项 + 一个标注）

README 摘录、完整文件树、文件体积、语言分布、依赖清单、完整度总分、代码行数、media **清单**（路径 + 字节数 + 类型）、以及一项**来源标注**：

- `source: 'platform'` —— 平台从制品解析出来的（九项里的前八项 + media 清单）
- `source: 'author'` —— 作者上传、平台**无法核对内容**的（截图/录屏的**画面**）

⇒ **契约要求**：dossier 的响应里每一项都带 `source` 字段，界面不得把 `author` 项呈现成「平台已校验」。这是 §6 闭集之外唯一诚实的处置。

## 6 增量 A · 承诺闭集（claims）

### 6.1 五条断言

| 断言 | 参数 | 今天核得动吗 |
|---|---|---|
| `paths_exist` | `string[]`（声明的关键路径） | ✅ 核得动 —— `asset_metadata.file_tree` 已持久化 |
| `entry_file_exists` | `string`（声明的入口文件） | ✅ 核得动 —— 同上 |
| `dependency_manifest_parses` | `ecosystem`（声明的清单生态） | ✅ 核得动 —— `asset_metadata.dependencies` 已持久化 |
| `min_code_lines` | `number`（代码行数下界） | ⚠️ **需要一列** —— 行数今天只被算进分数就丢掉了（`AssetMetadata` 没有 `code_lines`；Task 9 的 `codeLines` 因此恒为 `null`） |
| `declared_stack` | `string[]`（声明的技术栈） | ✅ 核得动 —— 断言存在要约上，比对 `asset_metadata.languages` |

**代价极小**：整档只需要 **一列**（`asset_metadata.code_lines`）+ 要约上一个 `claims` 字段（JSON，闭集校验后存储）。

### 6.2 它为什么有意义

今天 dossier 的九项**全是平台自己解析出来的** ⇒ 天生忠实 ⇒ **不可能违约**。而**作者说的话**（README 里写「这是一个完整的 XX 系统」、截图是「本项目运行效果」）今天没有任何核对。

闭集把「质量」翻译成「可核对的承诺」，于是：
- **说得越大，押得越多**（D7 的定价锚与这一节同源）；
- 违约变成一条**可机器认定**的事实，而不是一场口水仗。

### 6.3 闭集的纪律（照本项目既有标准）

- **闭集必须在类型层与运行期两侧收口**：`claims` 的解析器（zod）与 `judge` 的判据都从**同一张表**派生，禁止两处各写一份。
- **每一条断言都要有一个「不可能失败」的反向对照**：一条恒真的核对什么都没证明。
- **拒绝面必须与验收面成对**：每个断言都要有「声明为真 ⇒ 通过」与「声明为假 ⇒ 违约成立」两条用例。
- **不要**在这一版里加自由文本声明、加「我觉得」类条件（那是 P6 人工仲裁的事）。

## 7 增量 B · 机器审判（三段式）

### 7.1 触发与流程（按用户的原话固定）

交付 → 消费者自己先分析 → **一方申诉** → **才开庭**（机器审判） → 判罚**生效** → **才执行**。

平台**不主动判**，判罚**不自动落地**。申诉必须**指名一条闭集内的判据**（例：「我主张：要约声明 `paths_exist(['src/core/**'])`，而交付物里不存在」）—— 含糊的申诉不进入机器审判。

### 7.2 三条结论与对应判罚

| 机器结论 | 判罚（生效后执行） |
|---|---|
| **违约成立**（声明为假，或交付物 ≠ 钉住的那一份） | 单事务：**回转所有权**（两笔反向转让）+ **撤销对手方访问权** + **罚没押金**给受害方（`FORFEIT`，`feeBps: 0`）+ **信誉** −15 / −50 + 审计 |
| **违约不成立**（声明为真且交付物一致） | 申诉驳回；**申诉押注罚没给被申诉方**（D5）；**不**扣被申诉方信誉 |
| **不可判定**（事由不在闭集内） | 移出机器审判 → 人工仲裁（P6）；押金**保持冻结**，任何一方不得单方提取（沿用 §8.4「争议期间全额冻结」） |

### 7.3 防反咬（本节的承重性质）

**诚实方的交付物永远与自己的声明一致** ⇒ 机器驳回。恶意反咬因此**不可能靠含糊取胜**，而且在 D5 之下**有成本**。

一条对应的性质测试：*对任意一份「声明为真」的制品，`judge` 必须返回「不成立」*；反向：*对任意一份「声明为假」的制品，`judge` 必须返回「成立」*。

### 7.4 两条必须写进文档的边界

1. **「跑不起来」不是机器可判的。** D3 禁止平台执行用户代码，这条底线**不因本次改动松动**。这一类申诉只能走人工（P6）。
2. **回转只还所有权，不还保密性。** 源码一旦交付就无法追回。回转防的是「继续获利 / 继续转卖」，不是「已经看到的代码」。**这句话必须逐字出现在用户协议与争议说明里。**

## 8 增量 B · 押注（押金的量、来源与罚没）

### 8.1 形态

- **对称**：双方各押同一数额（D18 之下双方都能申诉 ⇒ 双方都能是违约方）。
- **冻结不是支付**：走 `freeze`（`USER_AVAILABLE` → `USER_FROZEN`），**不进** `PLATFORM_ESCROW`。⇒ 不变式 #4 的右式（托管 ≥ 未结算义务）**不因此改变**；押金属于用户的冻结余额，由既有的逐账户对账覆盖。
- **正常结束（`SETTLED` 且无申诉）⇒ 原额退还**（`unfreeze`），诚实交易**零成本**。

### 8.2 定价锚（D7 的可执行形式）

```
押金下限 = stakeFloor(claims)                    ← 默认档位表，可配置（照 §6.2 的先例）
         × (creditScore < 60 ? 2 : 1)            ← §10 已有的规则，不发明新参数
被要约方可以要求更高（对等加价）                    ← 双方合意的一个条款，平台不参与定价
申诉押注 = 固定小额档位（可配置）                    ← D5
```

**默认档位表的形状**（数字是**默认值，可配置**，与 §6.2 的权重同一种处置）：

| 声明的强度 | 默认押金下限 |
|---|---|
| 无强声明（只有平台自产 dossier） | `0`（**免押**） |
| 声明了 `paths_exist` / `entry_file_exists` | 低档 |
| 声明了 `min_code_lines(n)` | 随 `n` 分档 |
| 声明了 `declared_stack` | 中档 |

⇒ **性质自洽**：免押的交换仍然可以做（冷启动不被堵死），而**「吹牛」直接变成「要押钱」**。

### 8.3 额度来源（必须一起给的处置）

MVP 的站内额度**只有管理员能发**（`POST /ledger/credits`）。押金要求会暴露「没有额度就换不动」的冷启动问题。处置（按 8.2 已经解决一半）：

1. **低档声明免押金** ⇒ 没有任何额度的用户**仍然可以完成等值互换**；
2. 需要押金的场景由管理员发放额度（今天已有的路径）；
3. **不做**「以作品为押」（那等于把处分冻结当押金用，会把 lien 的语义与押金的语义混在一起，且需要一条新的可罚没物）。

### 8.4 罚则的账本形状

```
押金冻结   DR 违约方 USER_AVAILABLE   CR 违约方 USER_FROZEN        kind=FREEZE
罚没       DR 违约方 USER_FROZEN     CR 受害方 USER_AVAILABLE      kind=FORFEIT
退还       DR 违约方 USER_FROZEN     CR 违约方 USER_AVAILABLE      kind=UNFREEZE
申诉罚没   DR 申诉方 USER_FROZEN     CR 被申诉方 USER_AVAILABLE    kind=FORFEIT
```

**零新增 kind、零新增账户类型、零账本逆向。** 每一笔都有确定性幂等键（`exchange:stake:{contractId}:{userId}` 等），因此重复裁决只会重放。

### 8.5 据实记载的局限（不隐瞒）

1. **站内额度不可提现**（§8.1）⇒ 罚没给受害方的是**站内分，不等于损失**。它抬高的是欺诈成本，不是赔偿。
2. **额度可被管理员无限发放** ⇒ 在真实支付接入之前，押注的威慑力上限由运营纪律决定，而不是由机制决定。这与 §15 风险登记里「保证金威慑力不足」是**同一条已承认的风险**，本设计不假装解决了它。
3. **回转不能追回已下载的源码。**

## 10 锁的语义：处分冻结（lien）与解锁点

**定义**：`asset.assets.locked_at` + `holder_contract_id` 表达的是**处分冻结**，语义是「这件作品的处分权被一份合约占用」。

**生命周期**（本设计把它写死）：

```
lockAssets      在双方确认锁定之后（Task 7）
保持锁定         VALIDATING → RELEASED → 争议期（无论是否 DISPUTED）
unlockAssets    只在两个终态之一：SETTLED（含 RESOLVED_*）或 CANCELLED
```

**必须落地的三件事**：

1. **`CANCELLED` 与 `SETTLED` 两个终态都要解锁** —— 今天计划里 `unlockAssets` **零调用方**（§2.4），不修就是「作品永久卡死」。
2. **上传路径要检查 `locked_at`** —— §6.3:284 的「不可编辑」今天没有任何执行点。
3. **`RELEASED` 之后、争议期内不解锁** —— 这正是 §7.2「不可判定时押金保持冻结」在作品侧的对应物：`proposeOffer` 已经拒被锁定的作品（P3 计划行 2973），因此**欺诈方在争议期内无法把刚到手的作品再换出去**。

**复访触发条件**：P4 的拍卖路径落地时，必须把同一条检查接上（`locked_at` 非空 ⇒ 不得上架/成交），否则 lien 会在拍卖那一侧漏掉。这一条要写进 P4 的计划前言。
